# 中心融合加速：实现、回归与性能证据

目标：六相机的一组点输入在中心完成三角化、三机体位姿和 Kalman 更新，满足 60 Hz 的
16.667 ms 服务时间预算。当前输入来自原有 600 帧视频检测缓存，采样时间仍为 30 fps；
这项测试验证中心计算成本，不把素材改名为原生 60 fps 数据。

本页保存第一轮优化记录。第二轮进一步减少输入检查/局部几何开销，中心均值 10.23 ms、
P99 15.07 ms；可选浮点质心的精度取舍见 [进一步优化](further_optimization.md)。

## 实现

### 1. 缓存固定相机几何

`adapters/low_cost_mocap/multi_view.py` 按每台相机 K/R/t 的**数值快照**缓存投影矩阵与
相机对基础矩阵。缓存最多保留 8 套几何；标定数组即使原地修改，也会生成新键，避免误用
旧基础矩阵。缓存内容是不可变标定快照，不保存观测或时间状态。

### 2. 保持搜索次序的批量三角化

- 每个相机对批量求极线、计算点到极线距离，保持 5 px 门限和原有 `argsort` 次序。
- 候选记录相机内点索引。以惰性笛卡尔积遍历候选，消除原有大量 `deepcopy`。
- 后加入的相机仍是候选枚举的外层循环；最小重投影误差相同，仍选先出现的候选。
- 分批生成 `AᵀA` 并调用 NumPy 批量 SVD，工作数组每批最多 2,048 个候选。
  这是内存分批，不是候选数量上限，也不丢弃候选。
- 每个相机一次 `cv.projectPoints` 为整批候选打分，保留原来的 float32 世界点和像素输出
  约定、原相机 K/R/t、缺路槽位以及像素平方残差均值。

`helpers.find_point_correspondance_and_object_points` 已使用这个实现；独立流水线和 Web
应用都通过同一入口调用。原循环实现保留为
`find_point_correspondance_and_object_points_reference`，用于数值回归。

### 3. 刚体几何计算合并

- 一次广播计算整帧三维点距离矩阵，避免逐点调用小数组求和。
- 参考三角形的边长筛选向量化，按 C 顺序枚举 apex/base0/base1，保持上游选择次序。
  分块处理 apex 维，避免构造完整的大型 N³ 掩码。
- 第四标记距离批量求值，保持最近点的首项胜出与共享点所有权。
- 三点分支没有找到额外标记时，复用第一次 Kabsch 解。
- 两种底边顺序先比较数值证据，只给胜出分支生成欧拉角与对外字段。
- 3×3 Kabsch 协方差使用 OpenCV 双精度 `SVDecomp`，继续强制 proper rotation，
  镜像点集不会被当成合法旋转吸收。

### 4. 多轴低通合并调用

`LowPassFilter.filter` 用一次 `lfilter(..., axis=0)` 处理各列，取代逐列 Python 回调。
原系数、历史窗、窗截断与初始化语义均由完整轨迹回归约束。

## 如何验证

```powershell
.\.venv\Scripts\python.exe -m pip install matplotlib
.\.venv\Scripts\python.exe -m unittest discover -s tests
.\.venv\Scripts\python.exe tools\benchmark_fusion.py --repeats 3 --out out\rig3\fusion_current.json --baseline-report out\rig3\fusion_before.json --cpu-label "Intel Core i7-1255U (10 cores, 12 threads)"
```

`--baseline-report` 要求缓存、配置和环境相同；其他计算机应先建立自己的基准。
当前版本的 `--backend reference` 可以比较旧版跨相机搜索，但刚体部分仍为当前实现；
完整优化前基准是已有 `fusion_before.json`，其中记录了测量时所有源码 SHA-256。

- 输入为 `tracking_from_video.json` 中实际解码视频得到的点，完整序列逐帧处理。
- 按原捕获时间更新有状态的关联与 Kalman，不并行打乱连续帧。
- 比较完整输出结构、相机/点/刚体顺序、整数身份、姿态模式、失锁与所有浮点字段。
- 离散值严格一致；浮点叶值允许 `atol=1e-8, rtol=1e-7` 的舍入差，另报告 p/v/a、
  pose_t 和旋转矩阵的最大差。批量 SVD 与原库不同，不能把数值等价称为整个 JSON 逐位相同。
- 单元测试覆盖异构内参、缺第一/中间相机、重复像素、候选分批边界、噪声和原地修改标定。
- 计时仅包围实际 `process_detections`；解码、网络、结果比较与 UI 不计入。
  预热 10 帧，再按完整序列测量，记录 P50/P95/P99/最大值及所有逐帧耗时。

## 已测阶段

同机 i7-1255U，Windows 11，Python 3.13.5，OpenCV 5.0.0；中心 OpenCV 线程数固定为 1。
各次运行独立测量，输入/门限/跟踪配置相同。累计文件记录便于复核加速来自哪个阶段。

| 阶段 | 均值 ms | P95 ms | P99 ms | 完整序列数值回归 |
|---|---:|---:|---:|---:|
| 优化前 `fusion_before.json` | 111.137 | 193.911 | 328.336 | 600/600 |
| 几何缓存与批量三角化 `fusion_batched.json` | 23.912 | 30.921 | 38.044 | 600/600 |
| 刚体向量化与延后字段转换 `fusion_vectorized.json` | 14.747 | 17.673 | 20.922 | 600/600 |
| 小矩阵/滤波优化后，3 次完整序列 `fusion_optimized.json` | **14.864** | **19.972** | **23.768** | **1,800/1,800** |

相对本轮基准，平均服务时间缩短约 **7.48 倍**，均值倒数约 **67.3 组/s**。
但 1,800 次中仍有 **19.39%** 超过 16.667 ms，P99 也超过预算，**不能据此宣称稳定 60 Hz**。
三次测量的均值分别为 13.63/14.74/16.23 ms，显示运行环境/持续负载对时延有影响。
还需进一步缩短热路径、隔离 UI/编码负载，并做固定节拍、有界队列下的持续测试。

新算法已重新运行全部视频。滤波 p/v/a 与基线一致，原始位置最大舍入差约
`2.24×10⁻¹² mm`；定位分布详见 [优化版定位误差报告](position_accuracy_optimized.md)。

## 部署条件

中心计算达到帧周期后，实时链路还应做到：独立的点流生产者/组帧器、有界队列、单调的曝光
时间戳，以及独立的监控编码。现有 Web 应用同时做六路视频解码、图像检测、标注和 MJPEG，
其整体帧率不能直接用本页纯点输入的结果代替。已启动且关闭热重载的后端需要重启才能加载
新代码。

当前算法仍枚举原有所有极线候选，亮斑数异常增长时计算量会增加；新增机体或反光场景需重新
测量峰值负载。完整部署要求见 [边缘架构与部署评估](edge_architecture.md)。
