# 六相机边缘检测部署评估与设计

评估日期：2026-11-16。对象：6 路吊装 OV9281、3 架 Tarot 650、每机 4 个可见光标记，
机体原点位置/速度/姿态输出。采集与定位目标 **60 Hz**，监控视频 **15–30 fps**。

## 1. 结论与实现现状

**每相机就地检测、中心统一融合的切分合理。第二轮中心计算 P99 已进入 16.667 ms
预算，但仍有超时样本，端到端 60 Hz 真机链路与持续运行尚需验收。**
传感器和千兆带宽具备条件，决定能否落地的是中心计算吞吐、曝光同步、驱动支持及独立采集调度。

| 环节 | 已有证据 / 当前实现 | 部署判断 |
|---|---|---|
| OV9281 | 厂商规格 1280×800、最高 120 fps、全局快门、2-lane MIPI | 芯片支持 60 fps；模组、驱动、曝光/触发模式仍需逐项实测 |
| 检测与融合 | `TrackingPipeline.process` / `process_detections` 已分离 | 算法接口适合边缘化 |
| 软件等价性 | 独立本地进程解码、JSON 点包传递、逐帧比较，见第 4 节 | 仅证明已测输入及同一软件环境下的切分等价 |
| 真机边缘服务 | 尚无 OV9281 采集、点流网络服务与部署包 | 需实现 |
| 中心收包 | 验证工具只有离线严格组帧函数 | 实时 deadline、乱序/丢包/重启处理尚未实现 |
| 当前 Web 应用 | 浏览器 MJPEG 请求推动采集、处理和发布，共享 `_capture_lock` | 需要改为独立生产者；关闭/阻塞监控不能影响定位 |
| 曝光时间 | 文件用帧号；通用 RTSP/USB 路径用 host-arrival 时间 | 当前真流时间戳不满足同步动捕要求 |
| 60 Hz 定位 | i7-1255U 第二轮纯点输入均值 10.23 ms/组、P95 13.74 ms、P99 15.07 ms（3×600 组） | 本轮 CPU P99 达到预算；0.33% 超时，尚非端到端/硬实时保证 |

主要代码证据：

- `adapters/low_cost_mocap/tracking_pipeline.py`：输入完整相机列表或每相机点列表。
- `adapters/low_cost_mocap/video_replay.py`：`read()` 对直播源使用 `time.monotonic()`。
- `adapters/low_cost_mocap/low-cost-mocap/computer_code/api/index.py`：
  `/api/camera-stream` 的生成器调用 `cameras.get_jpeg()`。
- `.../api/helpers.py`：`get_jpeg → get_frames → _capture_mosaic → _camera_read`，
  处理、绘图、拼图/JPEG 与 HTTP 请求相连；记录 `max_skew_s` 但没有据此拒绝错位组帧。

## 2. 推荐物理拓扑与数据通路

```text
公共硬件触发源 ── 触发分配/必要的差分传输与电平适配 ──→ 六个模组 FSIN/XVS

CAM01 OV9281 ──短 CSI── Edge01 ──1 GbE──┐
CAM02 OV9281 ──短 CSI── Edge02 ──1 GbE──┤
CAM03 OV9281 ──短 CSI── Edge03 ──1 GbE──┤
CAM04 OV9281 ──短 CSI── Edge04 ──1 GbE──┼─ 千兆交换机 ─1 GbE─ 中心计算机
CAM05 OV9281 ──短 CSI── Edge05 ──1 GbE──┤                   ├─组帧/融合/发布 60 Hz
CAM06 OV9281 ──短 CSI── Edge06 ──1 GbE──┘                   └─监控/记录 15–30 fps
```

每节点一根以太网线至交换机，中心通过一个汇聚口接收六路；并非六根网线直接插入一个 PC 网口。
至少需要 7 个网络端口，通常选 8 口或更多。PoE 供电需要与板型匹配的 HAT/载板，按节点实测
峰值、转换效率及交换机总供电预算核算。相机和节点一起吊装，CSI 线保持短距离；支架刚性、
散热与镜头锁紧纳入标定稳定性设计，安装高度保持 ≤5 m。

**同一网线可以同时传点流与监控视频；公共硬触发另外需要触发连接。** 普通网线的空余线对
不能作为千兆链路之外的随意触发线。若要求现场只布以太网，需要支持 PTP 定时曝光的完整相机
或经过验证的边缘精密触发装置；给树莓派同步系统时钟本身不会让 OV9281 同步曝光。

### 每节点的两条处理路径

```text
同一次曝光/相机请求
  ├─原始单色图像 → 固定像素格式/旋转/去畸变 → 高斯/阈值/连通域 → 点包（60 Hz）
  └─有界监控队列 → 选帧/缩放 → H.264 编码 → RTSP/网关（15–30 fps）
```

中心负责极线匹配、DLT、刚体模板、四标记 Kabsch、时间关联、Kalman 及状态发布。
同帧所有机体共享点所有权，保留现有搜索次序。监控编码可以跳帧，检测不能依赖编码后再解码
的画面；两路共享 CPU/内存/NIC，必须限制监控队列与码率，才能避免间接拖慢定位。

### 边缘硬件与编码

- **Pi 4 有 H.264 硬编码器**，常用规格为 1080p30；官方也提供降低分辨率、调整编码
  level 等高帧率用法。本项目 1280×800@60 的采集+检测吞吐和编码模式仍要单独验证。
- **Pi 5 没有 H.264/H.265 硬编码器**，H.264 依靠软件。官方 2026 年测试显示特定低延迟
  配置可以实时编码 1080p30，约占单核 60%；这不是本项目检测+编码并行的实测。
  Pi 5 可作为 60 Hz 单节点验证的优先候选，配主动散热并限制软件编码工作量。
- 起步配置建议：原尺寸检测 60 Hz，监控 640×400 或 1280×800、15–30 fps、H.264。
  若监控也必须达到 60 fps，需要另做同时负载测试。不要默认选 H.265 软件编码。
- OV9281 输出 RAW8/RAW10。检测前固定到明确的 8-bit 灰度映射；RAW10 右移、黑电平、
  gamma/增益变化都会改变阈值语义。可见光模式使用可见光 LED，并核对模组/镜头 IR-cut 配置。

## 3. 60 Hz 的吞吐、时延与网络预算

60 Hz 是每 **16.667 ms** 一组同步的六相机观测，不是六相机合计 60 张图。

### 3.1 处理预算

流水线各阶段可以重叠。稳定 60 Hz 要求单节点检测及中心每组融合的持续服务速率均高于
60 组/s，并有处理尖峰的余量；不能只看平均值，也不能把端到端时延等同于帧周期。

建议工程目标（待验收，非当前实测）：

| 项目 | 目标 |
|---|---|
| 每节点采集/检测/发点 | 60 个不同曝光帧/s，处理 P99 <16.7 ms；争取 ≤10–12 ms |
| 中心组帧后融合 | 服务时间 P99 <16.7 ms；争取 ≤10–12 ms |
| 端到端 exposure-midpoint → pose publish | 明确测量时钟域，记录 P50/P95/P99，目标 P95 ≤25 ms |
| 缓冲 | 队列有界，不随运行时间增长；过期帧丢弃并计数 |
| 持续性 | 六路并行、监控开启，至少 30 min 温稳运行；报告每路及每机体的有效更新率 |

```text
端到端延迟 ≈ 半个曝光时间 + 传感器读出/CSI + 采集排队 + 边缘检测
            + 序列化 + 单向网络 + 等待组帧 + 中心融合 + 发布
```

点流单向发送，不应把网络往返 RTT 当作必经延迟。输出需同时带采样时间、发布时间与数据年龄；
当前 `statePre` 是采样时刻的先验估计，不是自动预测到网络接收时刻的状态。

第二轮中心纯点输入实测保存在 `out/rig3/fusion_round2_final.json`；第一轮记录保留为
`out/rig3/fusion_optimized.json`。
`out/rig3/edge_equivalence_optimized.json` 另测独立解码/检测进程与中心的分割；中心测量在
检测进程退出后进行，使用原有 OpenCV 线程设置，不包含浏览器绘图、JPEG、真实传感器、
网络和监控编码。`edge_worker_timing_contention_not_hardware_benchmark` 是同台 PC 上
争用资源的模拟节点计时，不能拿来承诺树莓派性能。

**优化前历史实测（`edge_equivalence.json`，i7-1255U，600 组）：**

| 路径/阶段 | 均值 ms | P95 ms | P99 ms |
|---|---:|---:|---:|
| 集中式六路解码 | 30.51 | 40.26 | 53.32 |
| 集中式六路预处理+检测 | 79.50 | 112.56 | 136.81 |
| 集中式检测+融合 | 189.06 | 286.56 | 404.83 |
| 集中式解码+检测+融合 | 219.57 | 315.32 | 445.80 |
| 边缘点包 JSON 校验/组帧 | 0.50 | 0.81 | 1.92 |
| 边缘化后中心融合 | **105.70** | **178.93** | **246.52** |

上述旧实现集中式均值倒数约 4.55 组/s，中心融合约 9.46 组/s，均不足实时 30/60 Hz。
在此基础上已经实施固定几何缓存、批量 DLT/重投影、刚体筛选向量化和小矩阵/滤波优化。

**优化前后纯点输入基准（同机环境、OpenCV 线程数 1，不包含解码/检测）：**

| 版本 | 均值 ms | P95 ms | P99 ms | 回归 |
|---|---:|---:|---:|---:|
| 优化前 `fusion_before.json` | 111.14 | 193.91 | 328.34 | 600/600 |
| 优化后 `fusion_optimized.json` | **14.86** | **19.97** | **23.77** | **1,800/1,800** |

均值倒数约 **67.3 组/s**，加速约 **7.48 倍**；但仍有 19.39% 服务时间超过 16.667 ms。
该第一轮均值只能说明中心计算接近 60 Hz，不能替代固定节拍、队列、热稳态和端到端
尾延迟验收。优化后重新解码视频的独立检测/中心等价验证同样通过 600/600 组，其中心融合
均值/P99 为 16.09/25.64 ms（原有线程设置），说明测试环境/负载对时延有影响。
实现和完整证据见 [中心融合优化](fusion_optimization.md)。
精度仍是在 30 fps **采样时间轴**上完整处理的结果，不代表原生 60 fps 精度或网络输出速率。

第二轮再做输入验证向量化、单候选免排序和局部几何值缓存，使用相同缓存与环境重测：
均值从 12.695 ms 降到 **10.226 ms**，P99 从 17.182 ms 降到 **15.069 ms**，
1,800/1,800 组完整输出与上轮逐位相同。仍有 6 组超出帧周期，最大 23.275 ms；
各次运行也有明显时间差异，不当作整套动捕系统的硬实时保证。
详见 [进一步优化及浮点质心取舍](further_optimization.md)。

优化前的前 60 帧 cProfile 显示，`find_point_correspondance_and_object_points` 占融合计时约
**86.7%**，`locate_bodies` 约 11.4%。这段样本中基础矩阵计算 3,847 次、投影矩阵组装
21,661 次、候选三角化 3,683 次、重投影打分 3,663 次。应处理重复几何计算、候选批处理和
Python 对象/数组开销；这些热点已作批量化优化，不应把旧 profile 当成当前版本耗时。
profile 的累计时间有父子嵌套且含插桩开销，不能与上表相加或当作未插桩吞吐。

### 3.2 带宽预算

原始灰度流的有效载荷：`宽 × 高 × 8 × fps`。1280×800 是 **1.024 MP**。

| 图像载荷 | 每相机 @30 fps | 6 相机合计 @30 fps | 每相机 @60 fps | 6 相机合计 @60 fps |
|---|---:|---:|---:|---:|
| RAW8 灰度 | 245.76 Mbps | 1,474.56 Mbps | 491.52 Mbps | 2,949.12 Mbps |

一根千兆线可以容纳单相机 RAW8@60，但六路原始流无法汇聚到同一个千兆上行；还未计协议开销。
RAW10 紧凑打包约增加 25%，16-bit 容器则翻倍。60 Hz 的点流数据量仍很小：

- JSON 点包包含相机号、采样序号、时间域、标定/检测版本等元数据；按实际序列化字节计费。
- 可选浮点质心模式使用完整浮点坐标，JSON 包通常比整数包更大；各节点必须统一模式，
  不得为省带宽再次取整。带宽按对应模式的实际点包长度重新核算。
- 测试按每相机每帧一包 UDP/IPv4 估算：点包外加 **66 B**（IP/UDP、以太网头/FCS、前导码/IFG），
  不含 VLAN；点包限制在 1472 B 内，避免 IPv4 分片。
- 监控按 **4–8 Mbps/路**做容量预算，6 路共 24–48 Mbps；默认报告选 6 Mbps/路。
  该码率是设计假设，不是编码器或链路实测。
- 精确结果见报告的 `bandwidth_source_fps` 和 `bandwidth_target_fps_projection`；
  后者保持监控码率不变，只按 60 Hz 外推点流。报告中的千兆剩余量是标称算术余量，
  还需考虑视频封装、IDR 突发与交换机队列。

本次点包最大 500 B（每相机每帧 8–12 个点），含完整协议元数据。由实际点包长度计算：

| 项目 | 30 Hz 点流 | 60 Hz 点流外推 |
|---|---:|---:|
| 6 路 JSON 应用载荷 | 0.717 Mbps | 1.434 Mbps |
| 6 路点流，含上述传输开销 | 0.812 Mbps | **1.624 Mbps** |
| 加上 6×6 Mbps 监控假设 | 36.812 Mbps | **37.624 Mbps** |

60 Hz 点流加监控约占标称千兆的 3.76%，网络容量有充足余量；表中没有假装测过实际编码器。

点流优先队列、监控码率限制、收发 socket 有界缓冲比升级 10 GbE 更优先。一个节点 1% 独立
丢包时，六路全部齐包的概率只有 `0.99^6 ≈94.15%`；只等待全齐包会放大有效帧损失。

## 4. 仿真视频的切分等价性验证

复现：

```powershell
.\.venv\Scripts\python.exe tools\edge_equivalence_check.py --frames 0-599 --target-fps 60 --reference out\rig3\tracking_optimized.json --out out\rig3\edge_equivalence_optimized.json
```

验证流程：

1. 六个本地进程各自打开一路交付视频，各自读取标定并调用同一检测器，正确解码指定帧号。
2. 每帧发送 JSON 字节点包。点的值和顺序完整保留，不传共享 NumPy 对象或真值标签。
3. 中心故意以反向相机到达次序读取点包，再按 CAM01…CAM06 恢复标定次序，严格核对帧号、
   时钟、配置和会话。比较各路解码像素 SHA-256，防止不同画面被视为同一帧。
4. 集中路径调用真实 `TrackingPipeline.process(images, t)`，边缘路径调用
   `process_detections(points, t)`，比较完整序列化结果及全序列哈希，覆盖 p/v/a、姿态、身份、失锁。
5. 如指定 `--reference`，与同版 `tracking_optimized.json` 逐位比较。与优化前
   `tracking_from_video.json` 的比较由 `benchmark_fusion.py` 完成，允许数值舍入差。

`--target-fps 60` 只用于预算和带宽外推，**源时间仍是 frame/30**。
把 30 fps 文件改成 `frame/60`、复制帧或把播放速度翻倍，都不能验证真实 60 fps 动捕。
测试也没有验证物理网络、实时收包策略、Pi/ARM 检测差异及实际同步；量产板上的相同点输入
仍应做回归验证，固定 OpenCV/算法与每相机标定版本。

优化后完整结果：**600/600 组像素相同、检测相同、融合结果逐位相同**。
两条路径的完整输出 SHA-256 均为：

```text
9e0a6486fe44e6c7ba109a1de2e10ee41bdb850c316056d755799b1e5dd3d68a
```

原有位置覆盖率 A/B/C 为 98.33%/100%/96.5%，三机同时有有效输出的帧占 **95%**。
等价通过包含了同样的失锁，不能解读为 100% 跟踪覆盖。
优化前历史报告 `edge_equivalence.json` 保留原始输出哈希；新旧版本不是整个 JSON 逐位相同，
但完整回归中滤波 p/v/a 完全相同，几何位置差仅为浮点舍入。定位分布见
[优化版误差报告](position_accuracy_optimized.md)。

### 旧结论勘误

早期脚本只在开始 seek 一次，却把接下来六帧标记成 `0,50,150,300,450,599`。
所以旧的“六个时段逐位通过”结论不成立，已由新版完整序列验证取代。
旧带宽表还把总字节率写成每路 kbps，链路余量计算重复乘了六次总点流。
旧文档“Pi 4/5 均有 H.264/H.265 硬编”“中心融合几毫秒”“PTP 即同步曝光”等表述均已修正。

## 5. 时间与坐标协议

建议点包至少携带以下字段；验证工具实现了其中的离线子集。

| 字段 | 含义 |
|---|---|
| `schema`, `session_id` | 格式版本和采集纪元；节点重启/重连不能与旧帧混组 |
| `camera`, `frame_id` / `trigger_seq` | 固定相机名与共同触发序号；各节点独立自增帧号不天然相等 |
| `exposure_midpoint_ns`, `clock_domain`, `exposure_us` | 曝光中心时刻及其时钟域，附同步质量；不用到达时间代替 |
| `calibration_sha256`, `detector_sha256` | 每相机标定/坐标约定和检测程序+参数版本 |
| `coordinate_space`, `image_size`, `valid`, `points` | 原生去畸变像素、实际尺寸、采集有效性、按检测顺序排列的点 |

绝对纳秒时间在二进制中用 int64；JSON 跨 JavaScript 边界时用十进制字符串或相对纪元，
避免超过 `2^53`。算法先以整数减去纪元，再转为相对秒。不得把一次无检测和一次相机未到包
混为同一种状态。

实时组帧器应按共同触发序号组帧，并检查曝光中心最大差值；固定相机槽位，即使缺路也不移动
K/R/t 下标。设置有限等待截止时间，过期/重复包计数后丢弃；允许满足几何条件的缺路融合，
否则显式发布 unavailable。中心按采样时间有序调用有状态跟踪器，不用迟到包让时间倒退。

PTP 解决时钟同步；外部触发/硬件定时曝光解决曝光相位。还须核对 NIC/驱动是否有硬件
timestamp、相机是否暴露 FSIN/XVS、驱动是否支持目标触发模式，以及时间戳对应曝光开始、
结束还是 CSI 接收。Arducam 官方说明支持取决于 **具体 SKU、板版本、固件与驱动**；
传感器标有 FSIN 并不能保证任意 OV9281 模组可通过同一 `trigger_mode` 命令使用。

Raspberry Pi 的 `rpicam --sync server/client` 另有软件帧相位同步功能，要求驱动正确支持
frame-duration 调节；跨设备时钟偏差会直接进入帧相位误差。官方“数十微秒”的描述针对同一
Pi 上相同型号相机的典型情况，不能外推为六块 Pi 的保证。此路径若用于仅布网线的方案，
需要在选定 OV9281 模组、60 Hz 及同时编码负载下独立验收，不等同于单独开启 PTP。

## 6. 对精度与鲁棒性的影响

### 6.1 曝光同步和运动模糊

同步误差造成的观测不一致量级为 `δx≈v_marker·δt`，其中
`v_marker≈v_body + ω×r`。下表仅是平移尺度示例，不是三角化最终误差的保证：

| 曝光中心差 | 1 m/s 标记 | 5 m/s 标记 |
|---|---:|---:|
| 0.1 ms | 0.1 mm | 0.5 mm |
| 0.5 ms | 0.5 mm | 2.5 mm |
| 1 ms | 1 mm | 5 mm |
| 5 ms | 5 mm | 25 mm |

毫米级预算下，建议先把最大曝光中心差控制到 **≤0.1–0.2 ms** 并实测；最终限值由最大
标记速度与误差预算决定。每秒 60 帧不代表曝光时间应为 16.7 ms：全局快门仍会运动模糊。
以 `f≈933 px, Z≈5 m, v⊥=5 m/s` 估算，1 ms 曝光拖影约 0.93 px；0.5 ms 约 0.47 px。
短曝光需要足够可见光标记亮度，固定曝光/增益，避免 PWM 与采样拍频。

### 6.2 标定、像素与机构

- `Z/f≈5.36 mm/px` 是 5 m 处单相机横向尺度；多视角可以减随机误差，但镜头畸变、
  主点偏差和外参漂移是系统误差，不会靠六相机平均自动消失。
- 相机方向漂移 0.05° 在 5 m 处约对应 4.36 mm 几何偏移；吊装振动、热漂与重新对焦后需复核标定。
- 四个标记的实测局部坐标、杆件刚度、固定点与机体原点定义直接影响 pose_t。
  姿态误差量级约为 `标记位置误差/有效灯阵基线`：1 mm / 0.46 m ≈0.125°。
- 当前整数质心、阈值 140、9×9 模糊与面积 3…200 保持等价基线。真实曝光、噪声、环境反光
  可能需要重新整定；更改检测器后重新比较失检、误检、身份和姿态，而非只看平均位置误差。
- `subpixel` 可选模式在仿真中减小 Z 偏差，但覆盖率略降、A 尖峰变大，故默认仍为整数。
  光斑几何中心不等于已校准光学中心，其真机效果不能由仿真误差直接外推。
- 仿真没有真实运动模糊、传感器噪声、镜头畸变或杆件挠曲；现有 3–4 mm 误差不是现场精度承诺。

### 6.3 60 Hz 对速度、加速度与滤波的影响

位置采样更密，但像素空间分辨率不因此提升。对独立的每轴位置噪声 σp，未滤波差分有
`σv≈√2·σp/Δt`、`σa≈√6·σp/Δt²`；30→60 Hz 时速度差分噪声约翻倍、加速度约四倍。
这些是差分模型量级，不是当前 Kalman 的最终误差。

真机 60 Hz 要用实际曝光时间差。当前 Butterworth 截止频率为 `sampling_frequency/3`，
30→60 时从 10 Hz 变成 20 Hz；Kalman Q/R 也需按实际噪声与采样时间整定。
`BodyTracker` 的 `reacquire_gap_s=0.5 s` 保持物理时间，但“3 次 misses”状态在 60 Hz 下
比 30 Hz 更早出现。`max_speed=10 m/s` 只是速度测量幅值上限，不是异常创新检验。

### 6.4 缺路、错帧和扰动试验

复现实际视频点缓存上的单因素试验：

```powershell
.\.venv\Scripts\python.exe tools\evaluate_deployment.py
```

逐一删除 CAM01…CAM06、加入 0.5/1 px 高斯质心扰动、令 CAM04…06 滞后一帧（33.33 ms），
以及加入交替方向的 0.05° 外参旋转误差。每个试验运行完整 600 帧，保持原 30 fps 时间轴，
使用真实匹配、Kabsch、时间关联与滤波。无真值身份进入估计器，计分最后才读取真值。

优化前的单因素结果保存在 `out/rig3/deployment_sensitivity.json`，同时报告条件误差、覆盖率、最长失锁和最近真值
机体检查。点级噪声不会模拟阈值失检、光斑粘连或曝光效应；单种子试验不是统计置信区间。
一帧错位是压力测试，不能据此插值声称 0.1 ms 错位的真实相机性能。

**优化前扰动试验（3 机体有效输出合并计分，姿态含有解的四点/三点先验帧）：**

| 单因素 | 三机同时有解 | 位置均值 / P95 / 最大 mm | 姿态均值 ° |
|---|---:|---:|---:|
| 基线 | 95.00% | 3.722 / 5.227 / 17.005 | 0.319 |
| 缺 CAM01 | 94.33% | 3.789 / 5.318 / 21.113 | 0.334 |
| 缺 CAM02 | 94.00% | 3.782 / 5.253 / 27.140 | 0.339 |
| 缺 CAM03 | 94.17% | 3.783 / 5.130 / 26.554 | 0.335 |
| 缺 CAM04 | 96.33% | 3.846 / 5.347 / 36.503 | 0.351 |
| 缺 CAM05 | 94.83% | 3.810 / 5.453 / 23.389 | 0.333 |
| 缺 CAM06 | 96.83% | 3.790 / 5.408 / 16.618 | 0.344 |
| 质心 σ=0.5 px | 94.67% | 3.955 / 5.832 / 20.348 | 0.515 |
| 质心 σ=1 px | 94.83% | 4.696 / 7.933 / 25.080 | 0.872 |
| CAM04…06 滞后 33.33 ms | **74.17%** | **17.349 / 29.603 / 87.229** | **2.298** |
| 各机交替 ±0.05° 外参旋转 | 94.83% | 3.740 / 5.257 / 21.941 | 0.320 |

结论：

- 单路缺失在本场景通常仍能工作，但缺 CAM01 时最长连续失锁达到 10 帧（0.333 s），
  比基线最长 3 帧更长。覆盖变化不单调，反映候选匹配/门限的影响，不能推论删相机更优。
- 1 px 质心扰动时，位置均值增加约 26%，姿态均值从 0.319° 增到 0.872°；
  速度 MAE A/B/C 从 0.036/0.043/0.041 增到 0.044/0.056/0.053 m/s。
- 错帧组观测既会失锁，也可能输出错误姿态：该压力测试旋转误差最大 **154.29°**。
  最近真值机体检查未发现错 ID，仍不能将其解释为姿态可靠。
- 本次特定交替外参误差对均值影响较小，不代表普遍免疫于标定漂移；误差的方向、相关性、
  基线和遮挡都会改变结果。系统偏移应通过现场已知位置点/杆验证。
- 本段轨迹机体最高速度 A/B/C 为 1.55/2.56/1.85 m/s；本报告的 5 m/s 同步与模糊数值
  属于设计预算，并非本轨迹已验证的运动范围。

## 7. 实现优先级

1. **中心尾延迟**：第二轮均值/P99 为 10.23/15.07 ms。继续测量异常样本，检查候选数量
   增长、CPU 调度与热稳态；每次修改保持全序列回归，避免降低精度来掩盖速度问题。
   时间关联有状态，不能直接把连续帧无序分给不同进程。
2. **独立运行链路**：一个采集/组帧生产者，一个按时序融合工作器，HTTP/监控只消费已发布结果。
   把标注、拼图、编码从定位关键路径移出。记录实际服务时间和样本年龄。
3. **一个实物节点**：锁定模组 SKU/驱动/板型；验证 1280×800@60、短曝光、触发时间戳、
   检测+监控并行的 P99 与温升。`MOCAP_SOURCE_FPS=60` 不会自动配置相机硬件为 60 fps。
4. **六路同步与网络**：实现点协议、deadline/缺路状态、配置校验、重启纪元；验证公共触发
   下的曝光中心差，并在监控开关、拥塞、单节点断流时测定位更新率。
5. **60 fps 端到端精度**：使用原生 60 fps 真机采集/对应真值完成定位、测速、姿态与丢失统计；
   若另做 60 fps 仿真，需真实重采样轨迹和渲染，不能重复现有 30 fps 帧充数。
